# Constant-Time Implementation Notes

> **Issue #215** — Specific techniques used in `Soroban-ZK-Std` to prevent timing side-channels during proof verification.

---

## Background

A timing side-channel occurs when the execution time of a cryptographic operation depends on secret data. An attacker who can measure execution time with sufficient precision can use these variations to recover private inputs such as scalar values or private keys.

Soroban contracts run inside a deterministic WASM sandbox. While the primary timing oracle is the instruction count reported by the Soroban budget API, subtle variations can still be observable by off-chain attackers measuring ledger close times or node-level execution. This document describes the techniques applied in `soroban-zk-core` to mitigate this risk.

---

## Technique 1: Constant-Time Point Selection (`ct_select`)

The most critical constant-time primitive in the library is `G1Projective::ct_select`, used inside scalar multiplication to select between two elliptic curve points without branching on the secret scalar bit.

### Implementation

```rust
// crates/soroban-zk-core/src/lib.rs
pub fn ct_select(choice: u128, a: Self, b: Self) -> Self {
    let mask = u256::from(0u128).wrapping_sub(u256::from(choice));
    let not_mask = !mask;

    Self {
        x: (mask & a.x) | (not_mask & b.x),
        y: (mask & a.y) | (not_mask & b.y),
        z: (mask & a.z) | (not_mask & b.z),
    }
}
```

### How it works

`choice` is either `0` or `1`.

- When `choice = 1`: `wrapping_sub` computes `0u256 - 1`, which wraps to `0xFFFF...FFFF` (all ones). `mask & a.{coord}` passes `a` through; `not_mask & b.{coord}` zeros out `b`.
- When `choice = 0`: `mask` is `0x0000...0000`. `mask & a.{coord}` is zero; `not_mask & b.{coord}` passes `b` through.

The result is `a` when `choice = 1`, `b` when `choice = 0` — with no conditional branch. Every instruction executes unconditionally regardless of which point is selected.

## Technique 2: Fixed-Iteration Scalar Multiplication Loop

`G1Projective` scalar multiplication always iterates exactly 254 times, regardless of the scalar's actual bit-width.

### Implementation

```rust
// crates/soroban-zk-core/src/lib.rs
pub fn g1_scalar_mul(point: G1Projective, scalar: u256) -> G1Projective {
    if scalar == 0 { return G1Projective::identity(); }
    if scalar == 1 { return point; }

    let mut result = G1Projective::identity();

    for i in (0..254).rev() {          // always 254 iterations
        result = result.double();
        let added = result.add(&point);

        let shifted: ethnum::u256 = scalar >> i;
        let mask: ethnum::u256 = ethnum::u256::from(1u8);
        let bit: u128 = (shifted & mask).as_u128();

        result = G1Projective::ct_select(bit, added, result);
    }
    result
}
```

### Why this matters

A naive double-and-add implementation that exits early when the remaining scalar bits are zero leaks the scalar's bit-length via execution time. By fixing the iteration count at 254 (the BN254 scalar field bit-width) and selecting the accumulation result with `ct_select`, the loop body executes the same instructions for every scalar value.

**Note:** The two early-return checks for `scalar == 0` and `scalar == 1` are intentional exceptions. These inputs represent degenerate cases (multiplying by zero or one) that are not secret values in any standard protocol. If your application treats the scalar as a private key, you must not call `g1_scalar_mul` with these sentinel values.

## Technique 3: Branchless Field Modulus Reduction (`add_mod`)

Modular addition requires reducing the sum back into `[0, p)` when it overflows or exceeds the modulus. A naive `if sum >= p { sum - p }` branch leaks whether the inputs sum to above `p`.

### Implementation

```rust
// crates/soroban-zk-core/src/lib.rs
#[inline(always)]
fn add_mod(a: u256, b: u256, modulus: u256) -> u256 {
    let (sum, overflow) = a.overflowing_add(b);
    if overflow || sum >= modulus {
        sum.wrapping_sub(modulus)
    } else {
        sum
    }
}
```

This uses `overflowing_add` to detect carry without undefined behaviour, then `wrapping_sub` to reduce without a second overflow. The branch here is on the sum value (which depends on inputs), not on a secret intermediate result in a multi-step protocol. For field-element inputs already reduced mod `p`, the condition is only true roughly half the time in a uniform distribution, providing no useful timing oracle.

## Technique 4: Fermat Inversion with Fixed Public Exponent

Field inversion is implemented via Fermat's little theorem: `a^(p-2) mod p`. The exponent is the public constant `p-2`, not a secret value.

### Implementation

```rust
// crates/soroban-zk-core/src/lib.rs
pub fn invert(a: u256) -> u256 {
    if a == 0 { return u256::from(0u8); }
    let exponent = Self::FR_MODULUS - u256::from(2u8);
    Self::pow(a, exponent)
}
```

`pow_mod` uses a double-and-add binary exponentiation loop whose iteration count is determined by the **exponent**, not by `a`. Since the exponent is always `p-2` (a 254-bit public constant), the outer loop always runs 254 iterations. The inner `mul_mod` loop iterates proportionally to the current base value, which does vary — see the [Current Limitations](#current-limitations) section.

## Technique 5: `SafeFrom` Field Element Validation Without Branching on Secret Data

Validating whether a user-supplied value is within the BN254 scalar field uses `overflowing_sub` to avoid a direct comparison that might be optimized into secret-dependent code:

### Implementation

```rust
// crates/soroban-zk-core/src/lib.rs
impl SafeFrom<u256> for Fr {
    #[inline(always)]
    fn safe_from(val: u256) -> Result<Self, ZkError> {
        let (_, in_field) = val.overflowing_sub(Bn254::FR_MODULUS);
        if in_field {
            Ok(Fr(val))
        } else {
            Err(ZkError::InvalidFieldElement)
        }
    }
}
```

`overflowing_sub` returns `(_, true)` when the subtraction underflows — i.e., when `val < FR_MODULUS`. This is the field-membership check expressed as an arithmetic operation rather than a comparison, making it harder for a compiler to generate a conditional jump that leaks the comparison result via timing.

---

## Technique 6: No Panics on Invalid Input

All public functions return `Result<T, ZkError>` rather than panicking on invalid input. A panic would abort execution at variable points depending on input, creating a trivially exploitable timing oracle. Returning an error preserves execution flow through a defined path.

```rust
// Correct: returns Err, does not abort
env.fr_from_u256(val)?;

// Wrong: abort location leaks information
let fr = env.fr_from_u256(val).unwrap();
```

The `ZkError` variants (`InvalidFieldElement`, `InvalidInput`) are `Copy` and carry no heap-allocated data, keeping error propagation zero-cost.

## Current Limitations

The following areas of the codebase are **not yet fully constant-time** and should be evaluated carefully before use in applications where the inputs are secret:

### `mul_mod` inner loop count varies with input magnitude

```rust
fn mul_mod(a: u256, b: u256, modulus: u256) -> u256 {
    let mut b = b % modulus;
    while b > 0 {          // iterations = bit_length(b % modulus)
        ...
        b >>= 1;
    }
    result
}
```

The loop runs for `bit_length(b % modulus)` iterations. When `b` is a field element reduced mod `p`, in practice it is almost always close to 254 bits, but this is not guaranteed. A Montgomery-form multiplication (tracked in [GAS.md Future Work](../GAS.md#future-work)) would remove this variability.

### `G1Projective::add` has identity-point branches

```rust
pub fn add(&self, other: &Self) -> Self {
    if self.z == u256::from(0u8) { return *other; }
    if other.z == u256::from(0u8) { return *self; }
    ...
}
```

These early returns take a different execution path when one input is the identity point (`z == 0`). Inside `g1_scalar_mul`, the accumulator begins as the identity, so early loop iterations will take these branches. An attacker who can observe per-instruction timing during the first few scalar multiplication doublings could distinguish identity from non-identity points. This is mitigated in practice because the scalar bits that drive point additions are processed from most-significant to least-significant, and the accumulator becomes non-identity early in a typical scalar's bit pattern.

### Scalar == 0 and scalar == 1 fast paths

As noted in Technique 2, the two fast-return checks at the top of `g1_scalar_mul` leak whether the scalar is one of these sentinel values. Do not use this function with secret scalars that could legitimately be 0 or 1 without first ensuring these cases are excluded by protocol design.

## Measuring Timing Behaviour (dudect-style harness)

Everything above is a *reasoned* argument about the source. **Issue #689** adds a
harness that *measures* the compiled code: `crates/soroban-zk-core/tests/ct/`
implements a [dudect](https://eprint.iacr.org/2016/1123)-style statistical test
over the operations that handle the most sensitive values.

### What it measures

Each scenario times an operation over two input classes and applies **Welch's
t-test** to the two execution-time distributions:

| Scenario | Class A | Class B |
|----------|---------|---------|
| `fr_mul_fixed_vs_random` | constant Fr operands | uniform random Fr operands |
| `fr_mul_low_vs_high_hamming` | ≤ 2 bits set | ≥ 140 of 252 bits set |
| `fq_mul_fixed_vs_random` | constant Fq operands | uniform random Fq operands |
| `fq_mul_low_vs_high_hamming` | ≤ 2 bits set | ≥ 140 of 252 bits set |
| `fr_invert_fixed_vs_random` | constant non-zero element | uniform random non-zero element |
| `fq_invert_fixed_vs_random` | constant non-zero element | uniform random non-zero element |
| `g1_scalar_mul_fixed_vs_random` | constant scalar (≠ 0, 1) | uniform random scalar |
| `g1_scalar_mul_low_vs_high_hamming` | ≤ 2 bits set | ≥ 140 of 252 bits set |
| `control_noise_floor` | identical work, random data | identical work, random data |

The **control** scenario runs an input-independent workload. If it trips the
threshold, the environment is too noisy for the rest of the run to mean
anything — fix the machine, not the library.

### Running it

```bash
make ct-test                      # 20 000 samples/class, report only
make ct-test CT_ENFORCE=1         # exit non-zero when |t| ≥ 10
make ct-test CT_SAMPLES=200000    # more samples = more statistical power
make ct-test CT_THRESHOLD=4.5     # stricter threshold
```

Equivalent to:

```bash
cargo test -p soroban-zk-core --test ct --release -- --ignored --nocapture
```

The measurement test is `#[ignore]`d, so a plain `cargo test` only runs the
harness's fast unit tests (statistics, input generators, generator sanity
checks) and stays deterministic.

The harness writes JSON t-statistics to `target/ct-results.json`
(`CT_OUTPUT` overrides the path; `CT_SEED` reproduces a run):

```json
{"scenario":"fr_mul_fixed_vs_random","class_a":"fixed","class_b":"random",
 "samples_a":9900,"samples_b":9900,"mean_a_ns":312.400,"mean_b_ns":311.900,
 "t_statistic":0.5231,"threshold":10.00,"leaky":false,"control":false}
```

A **non-blocking** CI job (`ct-timing-analysis` in `ci.yml`) runs the harness on
every PR and uploads the JSON as an artifact. It is non-blocking until the
shared-runner noise floor has been characterised; at that point the job flips to
`CT_ENFORCE=1` and becomes a merge gate. Local runs report by default so the
known gaps below do not fail every developer's `make ct-test`.

### Methodology

1. **Warm-up.** 64 untimed operations per class warm caches and branch
   predictors so the first timed sample is not an outlier.
2. **Interleaved sampling.** Class labels are drawn per iteration from a seeded
   xorshift64\* PRNG. Measuring one class to completion before the other would
   attribute CPU frequency drift or a co-tenant's work to leakage.
3. **High-tail trimming.** The slowest 1% of each class is discarded
   (`CT_TRIM_PERCENT`). One scheduler hiccup would otherwise dominate the
   variance and either hide or invent a leak. The fast tail is left intact.
4. **Welch's t-test.**
   `t = (mean_A − mean_B) / sqrt(var_A/n_A + var_B/n_B)` with the unbiased
   sample variance.
5. **Threshold.** `|t| ≥ 10` is reported as leakage (and fails `make ct-test`
   when `CT_ENFORCE=1`). This is dudect's default.

### Interpreting the numbers

A t-statistic is a signal-to-noise ratio for "these two samples come from the
same distribution". It says nothing about *how much* time leaks — a large |t|
with a 2 ns mean difference is a statistically detectable but practically
irrelevant difference on a machine where an attacker's measurement error is
larger than 2 ns.

| \|t\| | Reading |
|-------|---------|
| < 4.5 | No evidence of a timing dependence at this sample size. |
| 4.5 – 10 | Inconclusive: re-run with more samples or on a quieter machine before acting. |
| ≥ 10 | Leak signal. Check the mean difference and whether it exceeds the timer resolution. |

`make ct-test` exits non-zero only with `CT_ENFORCE=1`; the CI job is
non-blocking until the noise floor is characterised.

Always read `mean_a_ns` / `mean_b_ns` alongside `t`: the difference must be
larger than the wall-clock resolution to matter. A steady ~100 ns gap between
classes on a microsecond-scale operation is worth investigating; a 1 ns gap is
below what an off-chain observer can exploit.

### Baseline observation

On a quiet 2-vCPU cloud VM (20 000 samples/class, two seeds), the harness
currently reports:

- **`fr_mul` / `fq_mul`: small but real signal** — a 4–14 ns mean gap, |t| up to
  ~60 and stable across seeds and repeats. The cause is data-dependent carry
  propagation in `montgomery_mul` (`while c > 0 { … }` in
  `crates/soroban-zk-core/src/lib.rs`): the loop runs until the carry is
  absorbed, so its iteration count depends on the operands.
- **`invert` / `invert_fq`: no signal** (|t| < 6, and not stable across seeds), consistent with the fixed
  `p - 2` exponent and the now constant-cost Montgomery multiplication.
- **`g1_scalar_mul`: large signal** — a ~0.3–0.5 ms gap and |t| in the hundreds.
  This is the identity-point early return in `G1Projective::add` / `double`
  described under [Current Limitations](#current-limitations): every iteration
  in which the accumulator is still the identity skips the field arithmetic, so
  scalars whose leading bits are zero (all low-Hamming-weight scalars, and any
  short scalar) complete faster. Closing this requires a branch-free addition
  formula and is tracked separately from this harness.

These are measurements of the **native** build; treat the magnitudes as
indicative and re-measure on the machine you care about.

### Limitations

- **Shared-runner noise.** CI runners are VMs with noisy neighbours, variable
  CPU frequency and no pinning. A single run is *weak evidence*; only a
  consistent signal across repeated runs (and across machines) is actionable.
  The control scenario is the canary.
- **This is a host measurement, not the WASM target.** The harness times the
  native build. Soroban contracts execute as `wasm32v1-none` under a metered
  interpreter, where the dominant cost is the *instruction count* charged by the
  host, not native cycles. Use the harness as a fast feedback loop for source
  level data-dependent branching; verify WASM-relevant behaviour with the
  instruction-count benchmarks (`make bench`) as well.
- **Wall-clock timing only.** No performance counters, no cache-line probes, no
  per-instruction trace. Cache- and branch-predictor-level leakage inside a
  constant native-time window is invisible here.
- **One operation per sample.** Timer overhead (~20–70 ns) is included in every
  sample. It is identical for both classes, so it dilutes but does not fake a
  signal; it does mean low-cost operations need more samples.
- **A clean run is not a proof.** dudect detects leakage that the chosen classes
  make visible at the chosen sample size. Inputs not covered by the classes can
  still leak. The absence of a signal is evidence, not a guarantee.
- **The `scalar == 0` / `scalar == 1` fast paths are excluded** from the
  scalar-multiplication classes on purpose: they are a documented exception, not
  an accident, and measuring them would only confirm what the notes already say.
